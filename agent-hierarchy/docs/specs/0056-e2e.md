## Step 3 detail

Config: `roles.implementor` = `{"model":"inherit","dispatch":"model"}`, and `roles.ui-implementor`
gained `"dispatch":"model"` (the config's value for the subagent route). The capture hook was in
`<e2e>/.claude/settings.json`.

Run: `claude -p '<two tasks, dispatch per Roles + ROUTING, do not implement>' --model sonnet
--permission-mode acceptEdits --output-format stream-json --verbose --max-turns 40`, cwd `<e2e>`,
with a 900 s alarm. It exited 0 after 9 turns.

What happened:

1. **The routing decision was correct.** From the Orchestrator's final message: "A is UI work, so
   it goes to `ui-implementor`. B goes to `ah:implementor`."
2. It created both request skeletons through the CLI (`msg.mjs new --to ui-implementor …` and
   `msg.mjs new --to implementor …`), which confirms that `msg.mjs new --to <custom role>` works
   live.
3. Its `Write` to fill the first brief was refused by Claude Code itself:
   `Claude requested permissions to edit /private/tmp/claude-501/ah-0056-e2e/.claude/hierarchy/msgs/20260923-223553-1wle--ui-implementor--submit-button--request.md which is a sensitive file.`
   A headless session cannot answer that prompt. The message-file gate needs the filled brief, so
   the Orchestrator stopped, correctly without working around the block, and dispatched nothing.

This is an **environment blocker, not an 0056 defect**: Claude Code treats files under `.claude/`
as sensitive and prompts for writes there, and `-p` cannot prompt. The same would happen with the
built-in roles only. Any headless run of the message-file protocol hits it.

Options to unblock (a choice for the Orchestrator/user, so not taken):

- run with `msgs: "off"` in the e2e config: the gates then skip message files, and dispatch goes
  straight to the Agent tool;
- add a permission rule to the e2e `.claude/settings.json` allowing Write/Edit on
  `.claude/hierarchy/msgs/**`, if Claude Code honours an allow rule for its sensitive paths;
- run step 3 interactively (a pane session), where the prompt can be approved.
