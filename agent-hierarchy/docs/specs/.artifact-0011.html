Agent-hierarchy · design spec

Multiple rosters,
one repo.

Today, every orchestrator in a working directory shares one team.json, one peers.jsonl, one prefix. Spec 0011 lets N independent teams coexist — scoped by tagging records, not by splitting the hierarchy directory.

01 — Goal

Nothing stops two orchestrators sharing a directory.

Two top-level sessions — or two /pane sessions — in the same working directory resolve to the identical teamPrefix, the identical team.json, the identical peers.jsonl. The second create --spawn either fights the first team or silently adopts it.

Backward compatibility is a hard requirement. A repo with exactly one orchestrator must behave identically to today, with zero extra setup.

02 — History

Two amendments, both self-corrections

The mechanism changed shape twice after evidence — not opinion — invalidated its own premises. Both times, the correction shrank the design.

Original — withdrawn

Directory scoping

Scope the whole hierarchy directory per team: <dir>/teams/<name>/ holding its own team.json, peers.jsonl, msgs/. Motivated by a claim that one team's brief could reach another team's peer.
Amendment (a)

Evidence killed the premise

The mis-delivery claim was false — briefs travel as absolute paths over SendMessage, never by directory polling. Real damage was contaminated counts, not misrouted work. Directory scoping dropped in favor of the user's own proposal: shared files, tagged records, filtered on read.
  • ~4 call sites need to change, against 20 for the directory approach.
  • Requires the spawned peer to know nothing — decisive, since no env channel to a spawned peer exists.
  • Untagged records degrade to the default team for free. Migration is a no-op.
Amendment (b) — post-review

A gate went dark

Review found three defects, all in the spec, all accepted. The most serious: a hook exemption written before amendment (a) was never re-checked against it, and spec 0009's safety gate silently stopped firing for named teams. Traced to one file, then found in three more.
03 — Mechanism

One shared set of files. Only team.json splits.

Team identity is carried by the peer's name and resolved against the caller's own team.json — never by where a file lives.

<hierarchyDir(cwd)>/ team.json ← the default team (today's file, untouched) teams/<name>.json ← one file per named team, same schema peers.jsonl ← shared, records tagged, filtered on read msgs/ ← shared, frontmatter tagged, filtered on read gates.jsonl ← shared, unchanged

Not conceded

  • team.json still splits per team — one slot describing one team's membership can't be coherently tagged.
  • The naming prefix is still team-scoped. Tagging fixes what this tool reads; it does nothing about ListAgents, which is machine-global.

04 — Resolution logic

Two different questions, previously conflated

The original design answered "which team am I in?" everywhere, including where the real question was "which team owns this name?" — and the second question needs no session identity at all.

(A) Which team owns this name?

Asked by anything resolving a peer name to a role. Search every team file for a member with that name — works identically in hooks with a session id, hooks without one, and CLIs. This is the primary mechanism.

(B) Which team am I in?

Only asked when no name is in hand — an orchestrator scoping its own create or state block. Resolved by a four-rung fallback:

  1. Explicit --team <name> flag. CLIs only.
  2. Session id match against a team's orchestrator.session_id — available in hooks that receive one (e.g. route-gate, sessionstart); not in posttooluse-roster.mjs.
  3. CLAUDE_PID match against a team's orchestrator.pid, gated by pidAlive. This is what actually delivers "omit --team after create" for the CLIs — a recycled pid from a dead orchestrator must never match.
  4. Fall through to the default team. Today's behaviour, exactly.

07 — The gate blackout

Finding B3 — blocking

Security-adjacent · confirmed at source · widened past the original report

A safety gate stopped firing, silently, for named teams.

Route-gate was exempted from every team-scoping change on the grounds that hierarchyDir is no longer re-scoped. True — and irrelevant, because amendment (a) had already made the prefix and every name-lookup team-sensitive, and the exemption was never re-checked against that.

:235resolveConfig(cwd) — no session id passed, even though one is available two lines later.
:237teamPrefix(cwd) — unscoped.
:254–259All three role-resolution paths miss a named team's own members. No roleFromName fallback exists on this path.
→Role resolves to null. Spec 0009's global-scope confirm gate and the route-preference gate both stop evaluating — for a named team, silently.

Wider than reported. The same single-argument teamPrefix(cwd) call also appears in pretooluse-msg-gate.mjs, pretooluse-ultra-gate.mjs, and posttooluse-roster.mjs — three sites no prior file list had named.

Deliberate: widen the fallback

Route-gate gains the same roleFromName fallback roleForPeerName already ends with. A previously-null name now resolves to a role — a real behaviour change, named rather than smuggled in.

Must not change: the failure posture

null role must keep allowing. Flipping to fail-closed would contradict 0009 §8.12's deliberate fail-open design and could wedge a session.

09 — Confidence & lessons

High on the mechanism. No escalation.

The original escalation trigger — "if peers can't get a team scope without a race, ask Ultra-Advisor how" — came back negative, and turned out to be the wrong question. Peers need no team scope at all. Four self-reported defects share one shape.

01

Asserted a delivery mechanism never traced. The claim that a brief could reach the wrong team's architect drove the entire withdrawn design — and was false.

02

A test asserted an unverified fact. "Only one file calls hierarchyDir(" was flagged as unchecked, then built into a test anyway. 20 sites, 9 files.

03

Two absolutes stated without checking the baseline they had to coexist with. An existing test already required exactly the behaviour the new rule forbade.

04

An exemption survived a change to its own premise. The reasoning that justified it was true and irrelevant — the real dependency had moved.

When a spec is amended, every exemption and "not changed" claim must be re-derived against the new premise — those entries state a negative, and a stale negative is invisible.
